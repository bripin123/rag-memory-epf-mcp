# Judging protocol (frozen with qrels)
- Unit judged: chunk (with title + adjacent chunks shown). Document grade = max over its judged chunks.
- Scale: 0 = not relevant to the question · 1 = partially relevant (touches the topic/relationship but does not answer it) · 2 = relevant (a reader exploring this question would want this passage).
- Blind: judges see jid, query text, class (K/A/M), doc title, chunk text, previous+next chunk text. They never see channel, condition, scores, or other judges' output.
- Judge A = Claude (fresh subagent per corpus; record model id in the output file header) · Judge B = codex (record model id) · Adjudicator C = a fresh context that sees the query, the chunk, and both grades+rationales, and outputs a final grade. temperature 0 where the API allows.
- Input order: `pool/<c>.judge.jsonl` is shuffled with seed 20260817 + corpus index; judges process in file order.
- Gate: quadratic weighted kappa (A vs B) per corpus and per class >= 0.67 (thresholds.json kappa_gate_weighted). Below the gate: revise the rubric examples in this file, re-run BOTH judges on the whole corpus, discard the earlier outputs (keep them in pool/rejected/).
- Adjudication: every A/B disagreement goes to C. Human adjudication replaces C when the user has time.
- Human audit: `suite/human-audit.<c>.jsonl` = 50 pairs per corpus, stratified by class x final grade, including agreed items. Disagreement rate <= 20% -> qrels are `decision-grade`; otherwise or if absent -> `LLM-judged provisional` (no `remove-from-ranking` decision may be issued on provisional qrels).
- Prompt (identical for A and B): "You judge relevance for a retrieval evaluation. For each item output JSON {jid, grade, rationale<=25 words}. Grade 2 if a reader exploring the QUESTION would want this PASSAGE, 1 if it only touches the topic, 0 otherwise. Judge the passage as it stands; do not reward length or link count."

## Two-pass (D2)
- Pass 1: judges grade only the `tier: 'top30'` rows of `pool/<c>.judge.jsonl` (the same file, same blind shape; `tier` is present on every row but is not a judging signal — do not treat it as one). Once both judges finish pass 1, run `pool-deep.mjs <c>`.
- Saturation rule: `pool-deep.mjs` first resolves a conservative pass-1 grade per item — the adjudicated grade when one exists, otherwise `max(A, B)` (never `min`); this means any A/B disagreement can only make a query *more* likely to get its deep tier judged, never less. A query then qualifies for its deep (ranks 31-100) tier when at least one of its top30 documents is relevant (grade >= 1; document grade = max over that document's judged top30 chunks) and was surfaced by exactly one channel (channel union size 1 across that document's top30 rows) — i.e. the top30 pool for that query is not yet saturated.
- Budget and truncation: qualifying queries are granted their deep tier in ascending qid order until the running total of pass-1 rows plus planned pass-2 rows would exceed `thresholds.json judging_budget_per_corpus`; that query and every later qualifying query (in qid order) are then `truncated` for this run — their deep tier is never judged.
- Pass 2: `pool-deep.mjs` writes `pool/<c>.judge-pass2.jsonl` (the planned deep rows only — qualifying queries minus truncated ones — same blind row shape as `judge.jsonl`, in `judge.jsonl` file order) and `pool/<c>.deep-plan.json` (`qualifying`, `truncated`, `pass1_rows`, `pass2_rows`, `budget`). Judges grade `judge-pass2.jsonl` the same way as pass 1 and APPEND their rows to the same `pool/<c>.judge-A.jsonl` / `pool/<c>.judge-B.jsonl` files — pass 2 does not get its own judge-output files.
- `judge-merge.mjs` requires `pool/<c>.deep-plan.json` to exist (exit 11 otherwise). Its required items are every top30 row plus every planned deep row; deep rows that were never planned are excluded from `qrels.<c>.jsonl` entirely. Every qrels row belonging to a truncated query carries `pool_truncated: true` (all others `false`) — that flag means "this query's deep tier was never examined," which downstream consumers should not treat as "not relevant." The `qualifying`/`truncated` qid lists from `deep-plan.json` are copied into `FREEZE.md` when qrels are frozen (controller step).
