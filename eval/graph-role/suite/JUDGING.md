# Judging protocol (frozen with qrels)
- Unit judged: chunk (with title + adjacent chunks shown). Document grade = max over its judged chunks.
- Scale: 0 = not relevant to the question · 1 = partially relevant (touches the topic/relationship but does not answer it) · 2 = relevant (a reader exploring this question would want this passage).
- Blind: judges see jid, query text, class (K/A/M), doc title, chunk text, previous+next chunk text. They never see channel, condition, scores, or other judges' output.
- Judge A = Claude (fresh subagent per corpus; record model id in the output file header) · Judge B = codex (record model id) · Adjudicator C = a fresh context that sees the query, the chunk, and both grades+rationales, and outputs a final grade. temperature 0 where the API allows.
- Input order: `pool/<c>.judge.jsonl` is shuffled with seed 20260817 + corpus index; judges process in file order.
- Gate: quadratic weighted kappa (A vs B) per corpus and per class >= 0.67 (thresholds.json kappa_gate_weighted). Below the gate: revise the rubric examples in this file, re-run BOTH judges on the whole corpus, discard the earlier outputs (keep them in pool/rejected/).
- Adjudication: every A/B disagreement goes to C. Human adjudication replaces C when the user has time.
- Human audit: `suite/human-audit.<c>.jsonl` = 50 pairs per corpus, stratified by class x final grade, including agreed items. Disagreement rate <= 20% -> qrels are `decision-grade`; otherwise or if absent -> `LLM-judged provisional` (no `remove-from-ranking` decision may be issued on provisional qrels).
- Prompt (identical for A and B): "You judge relevance for a retrieval evaluation. For each item output JSON {jid, grade, rationale<=25 words}. Grade 2 if a reader exploring the QUESTION would want this PASSAGE, 1 if it only touches the topic, 0 otherwise. Judge the passage as it stands; do not reward length or link count."

## Two-pass (fixed depth 10 + predeclared depth-30 subset)
- Pass 1 (fixed depth 10): judges grade only the `tier: 'top10'` rows of `pool/<c>.judge.jsonl` (the same file, same blind shape; `tier` is present on every row but is not a judging signal). Pass 1 covers ranks <= 10 in every channel x condition list and every final list (off/on/fixed-pool with_graph), pooled over all 3 conditions (real, shuffled-r0, random) + purevec, for every A/M query — this is the metric-bearing pool for nDCG@10 and hit@k (k <= 10).
- Pass 2 (predeclared depth-30 subset): run `pool-pass2.mjs <c>` right after `pool.mjs` — it needs no judge output, because the subset is predeclared (chosen before any grade exists) precisely so it cannot be biased by outcomes. Candidate queries = every A/M query with >= 1 `top30` row (ranks 11-30); candidates are shuffled per class (A, M) with a seeded PRNG and picked in A, M, A, M, ... alternation, adding a query only if its whole top30-row count fits the remaining judging budget (skip-and-continue: a query that doesn't fit is skipped, not a stopping point — smaller later queries keep being tried). `pool-pass2.mjs` writes `pool/<c>.judge-pass2.jsonl` (the selected queries' top30 rows only, same blind shape, `judge.jsonl` file order) and `pool/<c>.pass2-plan.json` (`selected`, `not_selected`, `skipped_budget`, `per_class`, `pass1_rows`, `pass2_rows`, `budget`, `remaining_after`, `seed`, `generated_at`). Because pass 2 is fully predeclared, pass 1 and pass 2 may be judged concurrently — there is no need to wait for pass-1 grades. Judges grade `judge-pass2.jsonl` the same way as pass 1 and their rows land in the same `pool/<c>.judge-A.jsonl` / `pool/<c>.judge-B.jsonl` files (via `judge-batches.mjs merge ... --set pass2`) — pass 2 does not get its own judge-output files. Pass 2 is the metric-bearing pool for recall@30 (document-level) on the selected-query subset only.
- Ranks 31-100 (the `deep` tier) are never judged in Stage 1 — recall@100 is exploratory/non-estimable this stage. `pool/<c>.deepsample.jsonl` (100 rank-31-100 pairs, sampled uniformly without replacement) and `pool/<c>.unpooled.jsonl` (100 pairs from outside the pool entirely) are diagnostic-only missed-relevant-rate samples, not part of the depth-10/depth-30 metric-bearing qrels.
- `judge-merge.mjs` requires `pool/<c>.pass2-plan.json` to exist (exit 11, "run pool-pass2 first", otherwise). Required items = every top10 row + the top30 rows of `selected` queries only; top30 rows of non-selected queries and every deep-tier row are excluded from `qrels.<c>.jsonl` entirely. Every qrels row carries `judged_depth: 10` or `30` (30 for a `selected` query's rows, including its top10 rows) and `pool_truncated: true` unconditionally — ranks 31-100 are never examined for any query in Stage 1, so this is a blanket fact about this stage, not a per-query budget accident; downstream consumers should read `judged_depth` for coverage, not treat `pool_truncated` as "not relevant." The kappa gate is also computed separately (diagnostic, not gating) over the pass-1-only (depth-10) subset, printed alongside the main gate. The `selected`/`not_selected`/`skipped_budget` qid lists from `pass2-plan.json` are copied into `FREEZE.md` when qrels are frozen (controller step).
- Batch protocol: `judge-batches.mjs split <c> --set pass1|pass2|unpooled|deepsample [--size 25]` writes `pool/batches/<c>/<set>-NNN.jsonl` batch files plus a `<set>.index.json` manifest. Each judge grades a batch into `pool/batches/<c>/<judge>-<set>-NNN.jsonl`, first line a meta header `{"meta":true,"judge":"A","model":"<id>","at":"<iso>"}` (adjudicator C also carries `"role":"adjudicator"`), followed by `{jid, grade, rationale}` rows — judges must not see other judges' batch outputs. `judge-batches.mjs merge <c> --judge A|B|C --set ...` validates every batch (meta present, every batch jid graded exactly once, no foreign/duplicate jids, grade in {0,1,2}, rationale non-empty and <=25 words) and only then merges into the corpus-level judge-output files; `judge-batches.mjs status <c>` reports expected/present/valid batch counts per set and judge. Batch files show `prev_text`/`next_text` as a bounded window of at most `context_chars` characters nearest the passage (default 500; the cut is marked `…[cut] `); the full adjacent chunks stay in `pool/<c>.judge.jsonl`.
